## 1. Existing Lead Flow

**`PluginDownloadLead`** (`src/app/api/plugin-lead/route.ts`): Public `POST`, no auth guard (intentionally public, CSRF-exempt via `src/middleware.ts`). Rate-limited 20/hr/IP via `src/lib/rateLimit.ts` (DB-backed `RateLimitBucket` with in-memory fallback). Validates firstName/lastName/email/city + simple email regex. Inserts a row with `email` already `trim().toLowerCase()` at write time. Optionally SMTP-emails `digitalvurv@gmail.com` (graceful if unconfigured). Returns `{ id, success: true }` 201. **Never sets `prospectId`, never touches `Prospect`.**

**`BookingInquiry`** (`src/app/api/booking/route.ts`): Public `POST`, no auth, CSRF-exempt. Rate-limited 10/hr/IP. Validates name/email/message. Inserts a row — **`email` is only `trim()`ed here, NOT lowercased** (inconsistent with plugin-lead). Optionally emails `digitalvurv@gmail.com`. Returns 201. **Never sets `prospectId`, never touches `Prospect`.**

Both are serverless App Hosting request handlers. Their `status` column (`new|reviewed|replied`) is never transitioned by any code. Nothing today reads these back into the CRM.

## 2. Existing Agency / Ownership Flow

- **Agency context exists only in the authenticated session (`SessionUser.agencyId`, nullable).** Every prospect handler calls `requireAdminOrStaff()` and scopes queries with `user.agencyId!`: `findFirst({ where: { id, agencyId } })` (`[id]` GET/PATCH, intelligence, GTM) and `where: { agencyId }` (list). `Prospect.agencyId` is a **required non-null** FK to `Agency`.
- **Owner assignment (`Prospect.ownerId`, nullable, `ProspectOwner` → `User`) is manual and optional** — the create form and PATCH pass `ownerId || null`. **No default sales/admin owner and no assignment rule exist anywhere.**
- **Critical gap:** the public lead routes have no session and hence no agency context; `PluginDownloadLead`/`BookingInquiry` have **no `agencyId` column**. The only agency-ish signal is a single shared hardcoded recipient email (`digitalvurv@gmail.com`) — implying an implicit single-agency assumption, but nothing machine-readable binds a lead to an agency.

---

## 3. Matching Strategy

**Primary key = normalized email. Exact match only. No fuzzy or domain matching.**

1. **Normalize** lead email: trim → lowercase (`normalizeEmail`). Also normalize the stored `Prospect.primaryContactEmail` side at query time (stored prospect emails are unnormalized today).
2. If lead already has `prospectId` → return that relationship (idempotency, §7).
3. Candidate query: `Prospect.findMany({ where: { agencyId, primaryContactEmail: <normalized> } })`, ordered deterministically `createdAt ASC, id ASC` (never rely on arbitrary `findFirst` row order).
4. **Classify:** `0` → `created`; `1` → evaluate state (§6: `lost` → `requires_review`, `accepted` → `link`, else `link`); `≥2` → `ambiguous`, no link (§5).

**Why email-only:** no reliable second identity axis exists in the schema. Lead models lack org-normalized data usable for matching; `Prospect` org/domain fields (`websiteUrl`, handles, `industry`) are free-form and sparsely populated. Organization/domain matching (§H) is rejected as not safely determinable.

## 5. Duplicate / Ambiguity Handling

**Default to `ambiguous` — never auto-resolve.** When `≥2` Prospects share the same email (structurally possible; no unique email constraint exists — dedupe is app-level):
- Do **not** link.
- Return a structured `ambiguous` result listing candidate ids so a caller can surface it.
- Optionally record `agent.reconcile.conflict` audit + a staff notification (§10).
- Human resolves. The reconciler never silently attaches to the wrong Prospect. (Dedup/merge is a future concern, not P1.2.)

---

## 6. Lost / Accepted Prospect Handling

- **`lost`:** do **not** auto-reconnect and **not** auto-recreate. A `lost` email could be a new real opportunity (reconnect) or noise (keep lost) — not safely discernible deterministically. Treat single `lost` match as **`requires_review`** (audit, no write). Auto-reconnecting could resurrect a deliberately-closed prospect.
- **`accepted`:** an active opportunity/contact — **unconditionally link** to the existing Prospect (single deterministic match; clearly same email owner). Do not create a duplicate.
- Other single-match states (`new|researching|qualified|proposal`): **link** directly.

---

## 7. Idempotency Strategy

- **Primary guard: the existing `lead.prospectId` relation.** `prospectId` is a plain non-unique column (app-level a lead→Prospect link is 1:1). The reconciler **reads the lead and, if `prospectId !== null`, returns `already_linked`** before matching. `reconcile(lead)` ×3 converges to one link.
- **Concurrency / race:** two simultaneous first-time reconciles could both see "no link" and both create a Prospect → duplicate. Since no unique constraint exists on `prospectId`, use **serialized transaction + conditional update** (§8): `updateMany({ where: { id, prospectId: null }, data: { prospectId } })`; `count === 0` means the race was lost → roll back and return `already_linked`.
- **No new DB constraint required** with the conditional-update guard. If a hard guarantee is ever wanted, a unique index is identified — but a plain unique-on-email is itself incorrect (two distinct people may share an alias), so app-level protection is preferred and correct.

---

## 8. Transaction Strategy

Wrap reconcile in a **Prisma interactive transaction** (`prisma.$transaction(async (tx) => {...})`):
1. Read lead (inside tx).
2. If linked → return `already_linked`.
3. Match candidates.
4. If creating: create Prospect, then conditionally link the lead (`updateMany where prospectId null`), inspect `count`. On `count === 0`, **roll back** → return `already_linked`.
5. Link-only path runs in a tx for a single atomic `update`.

This makes Prospect-create + lead-link **atomic** — no partial writes — and serializes concurrent creations through the conditional update. Failure rolls back cleanly.

---

## 9. Audit Strategy

Use `src/lib/audit.ts` `logAudit(...)` (best-effort, never throws — repo convention). Minimum events:
- `agent.reconcile.create` — new Prospect (entity `Prospect`, entityId).
- `agent.reconcile.link` — existing Prospect linked.
- `agent.reconcile.conflict` — ambiguous (metadata = candidate ids).
- `agent.reconcile.requires_review` — `lost`/indeterminate single match.
- `agent.reconcile.failed` — error path.
- `agent.reconcile.already_linked` — idempotent no-op (optional; omit if noise).

Reconciler runs with no session (public/background) → pass `null` user, rely on `entities`/`metadata`. Preserves P0's "AuditLog immutable record; AgentEvent work-product" split.

---

## 10. Notification Strategy

Notify **only for staff-actionable events** (via `src/lib/notifications.ts` → `Notification`):
- **`ambiguous`/`conflict`** — notify staff (someone must resolve).
- **`lost` `requires_review`** — borderline; recommend **skip** in v2 (low volume, conflicts already audited).
- **New Prospect created** — **skip** (reconcile-on-insert volume would flood with no actionable need).

v2 recommendation: **notify only on `ambiguous`** (assuming a staff-addressing helper exists by P1.2).

## 11. Public Route Integration

**Recommend Option B — reconcile after insert, from outside the public request path.**
- **A (synchronous in-request):** adds latency + DB transaction to already-rate-limited public capture forms and couples the public response to dedupe health → avoid.
- **C (queue/background):** **no queue, cron, or background infra exists** (verified: only a client `setInterval` in `NotificationBell.tsx`). Introducing infra is out of scope.
- **B:** keeps the insert fast and isolated; a separate trigger (future cron/manual "Reconcile" admin endpoint/Agent Runtime) invokes the reconciler for `prospectId null` leads. Because it's **idempotent** and **email-exact**, running later/repeatedly is safe.
- Serverless timeout is addressed: reconciler runs off the hot public path; per-call work is one lead (bounded). The v2 driver is a sweep (`findMany where prospectId null`) — its wiring is a P1.2 tooling decision, not a schema/architecture change.

## 12. Security Model

- **Lead text is data, never code** — no LLM, no prompt templating, lead fields never rendered as executable instructions; writes are typed strings into typed columns.
- **Agency isolation:** every Prospect read/write is scoped by the passed `agencyId`; the reconciler is a pure function `(agencyId, lead)` that **fails closed** if no agency is supplied — never attaches to an arbitrary agency.
- **Public-input hygiene:** normalize email; treat names/org as trimmed, length-capped strings.
- **No secrets exposed:** reconciler uses no env credentials and sends nothing (SMTP stays in the public routes).
- **Rate limiting / CSRF preserved:** public routes keep 20/hr & 10/hr limits and CSRF exemptions (by design). Reconciler writes are **auditable** and, when invoked from an authed context, go through the existing `requireAdminOrStaff` guard.

## 15. Risks / Blockers
1. **RESOLVED — Agency context for public leads.** *(Originally a blocker; see §17 for the approved decision.)* Lead models have no `agencyId`; public routes have no session. The reconciled agency is now directed: a **configured/default `Agency`** (option (a)) is the authoritative agency context for Media MVP public-lead reconciliation. P1.2 resolves that default `Agency` deterministically and **fails closed** if it cannot be resolved. Option (b) — adding `agencyId` to leads — is **not** authorized for Agent 1.
2. **Email inequality across write paths** (`plugin-lead` lowercases; `booking` doesn't). Normalization in the reconciler absorbs it; normalize both sides at query time. No backfill.
3. **No unique email constraint on Prospect** — ambiguity is structurally possible; reconciler must never assume one (intentional app-level dedupe).
4. **No background infra** — Option B depends on a future cron/Agent Runtime driver; the trigger decision is a P1.2 deliverable.
5. **Version default mismatch** (`route` writes `plugin` `1.2.0` default vs schema `1.1.0`) — cosmetic, unrelated, noted.
